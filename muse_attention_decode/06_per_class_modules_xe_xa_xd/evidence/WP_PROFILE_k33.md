# PROFILE.md - where time goes in dev/k33.py on the 12 scored shapes (WP, 2026-10-28)

Kernel: `dev/k33.py` (base k33; one `kernel_fn` call = exactly one `attn_*` launch). Shapes: `tools/bench.py::shape_kwargs`
(ctx 80000, page 1, tp8, sliding = soft, full = coherent, `spread agentic` for B > 1). One Modal H200 container per job
(ncu 2025.3.1, nsys 2026.4.1, CUDA 13), SM clocks not locked (`--clock-control none`).

## How the numbers were taken (and what is ncu-only)

| source | what | perturbation |
|---|---|---|
| **nsys** (`dev/wp/run_nsys.py`, `nsys_loop.py`, `nsys_parse.py`) | the bench.py protocol: fresh inputs copied in, 512 MB `flush.sum()` (read flush, torch `reduce_kernel`, 131-135 us), `ev.record(); graph.replay(); ev.record(); sync`; 60 measured replays after 10 warm-ups (4 rotating input sets); `--cuda-graph-trace=node`. Kernel duration and the flush-end -> kernel-start gap come from the nsys kernel trace. | tracing overhead is small: the same loop without nsys gives an event total within 0.6 us of (nsys gap + nsys duration) |
| **event** (`*_plain.json`) | same loop, no profiler: event total, empty-graph event time (bench.py's "fixed graph cost"), event minus empty = bench-style time | none |
| **ncu** (`dev/wp/run_ncu.py`, `prof_one.py`, `ncu_extract.py`) | per shape: ONE kernel launch (the 3rd call, `--launch-skip 2 --launch-count 1`), `--set full` + 74 extra metrics (`metrics.txt`), `--cache-control all --clock-control none`, `--warp-sampling-interval 0` (finest pc sampling, 32 cycles), `-lineinfo`, source imported; plus a 1-pass duration-only run | **ncu-only**: replays the kernel ~40 times with cache flush, serialises it and slows it (ncu duration is 1.07-1.30x the nsys duration on the small kernels, 1.03-1.07x on the big ones). Every ncu-derived number below is labelled "(ncu)"; rates that mix ncu bytes with the nsys duration say so. |

Caveats that matter for reading the stall data:
* Pc-sampling shares are per **warp**, not per critical-path time. Every CTA is 16 warps (512 threads) with role specialisation, so warps parked
  at a CTA/cluster barrier (producers, idle lanes) inflate "barrier". Use the per-line tables to tell parked waits (`cl_wait()` at CTA exit)
  from working-warp stalls.
* Sample counts: d1s 1.5K, v1s 2.2K, d16s 4.5K, d32s 5.9K, v16s 6.1K, v32s 11.5K, d1f 10K, v1f 15K, 78K-159K for the four big full shapes. Line shares on
  the small kernels have roughly +-1 point sampling noise.
* "Nearest banner section" is the closest preceding `// ----` / `// ====` comment in the source string: a coarse hint (sections can span hundreds of lines), not a phase timeline.
* "Gather floor" figures quoted below (5.4-6.0 us @ 20.5 MB, 4.4 us @ 16.8 MB, 76.4 us @ 328 MB, 152 us @ 655 MB) come from docs/PLAN.md / WORKERS.md
  (dev/probe_gather.py), not from this profile.
* Not measured here: per-CTA phase timelines (dev/trace.py with -DK2_TRACE).

Raw reports: `dev/wp/raw/ncu/<tag>.ncu-rep` (+ `_1pass.ncu-rep`, `_details.txt`, `.json` = extracted metrics, `.log`),
`dev/wp/raw/nsys/<tag>.nsys-rep` (+ `_parsed.json` incl. per-replay series, `_plain.json`, `_nsys_events.json`), `dev/wp/raw/src/k33.cu` (the line-number reference),
`dev/wp/raw/probe/` (ncu metric catalogue for gh100). Tags: `d`/`v` = decode/verify, batch, `s`/`f` = sliding/full (e.g. `v16f`).
Tables are generated by `python3 dev/wp/make_tables.py dev/wp/raw` (`tables.md`).

## Per-shape top-3 bottlenecks

Format: bottleneck - evidence. "(ncu)" = ncu-only metric; unlabeled times/rates are nsys. Interpretation after the dash is mine; the numbers are measured.
`dur/floor` uses the TASK.md floor. L-numbers refer to `dev/wp/raw/src/k33.cu` (= the `SRC` string of k33.py).

### decode b1 sliding (d1s) - `attn_1_1_1_1s`, 2 clusters x 16 CTAs, 3.87 us (38.7x floor), DRAM 0.57 MB = 3% of peak
1. **Launch/entry on cold code and cold first loads.** front-end stalls (imc_miss + no_instructions) 13.7% of samples (ncu); entry lines L6211 (cluster-id/rank S2R reads, short_scoreboard 8.3%) and L6215 (imc_miss 3.2%); L6278 new-token loads long_scoreboard 4.7%; L2 hit 42% (ncu) = page table / qkv / positions come from DRAM after the flush; CTA-resident time per used SM is 3.0 us of the 5.0 us ncu duration (ncu).
2. **Cluster barriers dominate the stall mix.** barrier 42.5% of samples: L6373 `cl_wait()` 22.7% (warp group that finished its role, parked), L6477 9.0% (final wait), L6411 8.4% (phase-1 wait). Part of this is parked warps, so it overstates the critical path. The DSMEM payload is trivial (384 st.async, 139 KB, xbar throughput 0.3% (ncu), 224 set conflicts), so the cost is barrier/mbarrier round-trip latency, not bandwidth.
3. **Machine nearly idle during the one short gather.** 32 of 132 SMs hold CTAs (waves 0.24; SMs active 15% of elapsed cycles (ncu)); issue-active 24.6%, 0.38 eligible warps/scheduler, tensor 0.5%, XU 2.0%; remaining waits are single global/DSMEM round trips (long_scoreboard 7.8%, mbarrier wait L139 1.6%).

### decode b1 full (d1f) - `attn_1_0_1_1w`, 132 CTAs, 13.18 us (3.07x), DRAM 20.9 MB at 1.58 TB/s = 33% of peak
1. **Start burst / first tile.** ~25% of samples sit in the start section (banner @L4334): cp.async issue L4483 5.5%, scalar loads L4335/L4307/L4376 2.3-2.4% each, first QK wgmma L890 long_scoreboard 6.9% (waits for tile-0 data). DRAM at 33% of peak vs a gather probe of 5.4-6.0 us for this byte count => about 7 us of the 13.2 is outside the pure gather.
2. **Merge -> publish -> global combine chain.** barrier is the #1 stall (21.5%): L4839 7.6% (publish, `if (wsacc2)` after `__syncthreads`), L4751 5.9% (per-lane O store to smem before the merge), L4605 shuffles 2.6%; publish section 10.4% of samples; 2112 red.global instructions -> 26.9K L2 red sectors, 132 atomics.
3. **Pipes under-filled, cold code visible.** issue-active 38%, eligible 0.62, tensor 1.6%, XU 10.7% (ncu); front-end stalls 6.8%; SMs active 74% of elapsed (ncu): the kernel is a latency chain (start -> tiles -> merge -> combine), not a throughput problem.

## Cross-shape patterns

1. **The flush -> kernel gap is a constant 4.1-4.3 us for every shape and for the empty graph alike** (nsys, p10-p90 3.97-4.45 us; empty-graph 4.10-4.29 us), independent of grid, cluster launch, smem size or kernel length. The empty `add_` kernel in bench.py's "fixed graph cost" lasts 0.99-1.15 us, so the bench-style number (event total minus empty graph) equals our kernel duration minus ~1.05 us (measured difference 0.87-1.3 us on 11 of 12 shapes, 1.9 on v32f); the judge's "+~1 us per call" offset is that same ~1.1 us. Judge-visible time is therefore ~ the nsys kernel duration; the 4.2 us gap is common-mode and not ours to remove.
2. **Sliding shapes (46 of every 62 calls) are latency chains, not throughput problems.** They move 0.6-23 MB (2-39% of HBM peak), run 2.8x-56x over the floor (3.9-13.7 us), and show: issue-active 25-48%, 0.4-1.0 eligible warps/scheduler, tensor 0.5-9.7%, XU 2-8%. Stalls are barrier (21-43% of samples on the cluster kernels d1s/d16s/d32s/v1s) and long_scoreboard (8-30%), plus a 5-14% front-end share (imc_miss + no_instructions = cold instruction fetch after the L2 flush). Only 32-128 of 132 SMs hold CTAs (SMs active 15-79% of elapsed cycles (ncu)).
3. **Cluster/DSMEM cost is latency (barrier + mbarrier round trips), not bandwidth.** DSMEM payload is 0.14-3.5 MB per call (xbar throughput 0.3-4% (ncu)); the combine lines (`cl_wait`, mbarrier try_wait loop, `cl_arrive_relaxed`) carry 24-41% of samples on d1s, d16s, d32s, v1s, v16s (partly parked warps).
4. **Full layers at B = 16/32 are memory-system-bound, in two regimes.** Decode (run1 FLAT) reaches 3.84 / 4.06 TB/s (80 / 85% of 4.8 TB/s peak, 89 / 94% of the 4.3 TB/s gather ceiling); its top stall is long_scoreboard (28-30%) at the page-table -> cp.async address shuffle (L8988: 26-28% of samples) and tensor use is 3-4%. Verify (run8 FLAT) reaches only 3.38 / 3.69 TB/s (70 / 77%) and is issue/ALU-limited: issue-active 57-58%, ALU pipe 49-51%, tensor 26-27%, 1.2 eligible warps, 48 / 94M warp instructions vs 35.5 / 65.8M for decode; stalls not_selected 16%, wait 14-15%, math_pipe_throttle ~10%. Gaps over the gather floor: d16f +11 us, d32f +14 us, v16f +23 us, v32f +31 us.
5. **Full layers at B = 1 (13.2 / 17.0 us) use 26-33% of HBM bandwidth**; the 20.5 MB gather probe takes 5.4-6.0 us, so 7-11 us is start burst + merge/publish/combine chain (barrier is the top stall: 22% / 29%).
6. **Byte traffic is not the problem.** DRAM reads are 0.95-1.06x the mean-length K/V bytes on 11 of 12 shapes (extra = page table, q, partials); exception: v32s 1.19x (+3.6 MB, unexplained here); L2 request amplification at L2 on v1f (27.7 MB requested for 20.9 MB read) and v1s (0.76 MB for 0.61).
7. **Shared-memory bank conflicts are negligible**: 0.35-6.1% of smem wavefronts on ten shapes (v32f: 64K of 18.2M); 8.3% / 14.4% only on d1s / v1s where the absolute count is <= 8.4K. Global atomics/reductions are small (<= 2.5K red/atom instructions; 27-32K L2 red sectors on the decode-full shapes d1f/d16f/d32f).
8. **Register/smem residency:** every kernel runs 1 CTA/SM (512 threads, 117-226 KB smem, 60-128 regs); active warps per scheduler is ~4.0 (occupancy-limited at 25%), so latency hiding relies on in-CTA ring depth, not extra CTAs.

## Reproduce

```
bash tools/gate.sh tools/modal_run.py --cmd "python3 dev/wp/run_ncu.py --shapes '<b,L,layer;...>' --out /tmp/wp_out/ncu && python3 dev/wp/run_nsys.py --shapes '<...>' --out /tmp/wp_out/nsys --reps 60" --fetch "/tmp/wp_out" --tag wp_full
python3 dev/wp/make_tables.py dev/wp/raw > dev/wp/tables.md     # local, no GPU
```
Each of the two jobs (ncu: 12 shapes x (full set + 1-pass + extraction); nsys: 12 shapes x (plain + nsys + export + parse)) runs in under 10 minutes on one container.
Jobs: wp_full (ncu + first nsys pass) and wp_nsys2 (nsys re-run after fixing the empty-graph kernel classifier; dev/wp/raw/nsys is from wp_nsys2).
