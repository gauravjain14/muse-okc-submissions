# Agent K — m = 256 (verify-32) for o / pooler / unpooler (2026-11-02, phase 2)

Base to beat: claude/t3/bo6.py at m = 256: o -> `rl` (tt_v10 rl_early_projection: swapped A = W 64 rows packed,
B = x 256 tokens, 1 consumer WG, W by 1D bulk copy from a packed W), pooler / unpooler -> pinned cuBLASLt plans
(nvjet_sm90_tst_128x64_64x8 / 128x128_64x6). Deliverable: claude/t3/K/g256k.py (prepare_g256k / run_g256k, None outside
193 <= m <= 256 or other layers) + sub_g256k.py. Dev kernel: claude/t3/K/kg.py (copy of agent V's vg.py + the options
below); harness claude/t3/K/kt.py (same-run timing vs SGLang and bo6's m=256 routes rebuilt standalone, + traces).
All times local us (graph replay after a 512 MB read flush, empty-graph cost subtracted) unless noted.

## Shipped (current, iteration 3): g256k.py, cfg (TM, BN, LAY, S, NS, MC, RED, MAP, PERM, PF, PFX, EPI, PRO, PRI, LASTD, WPK[, NT2, EPF, XLD])
- o:        (128,128,0,1,6, 0,0,0,0, 0,0, 2, 1,0, 3, 2)  128x128 tiles (WG g: tokens 64g.. x 128 cols), 6 stages
- unpooler: (128,128,0,1,6, 0,0,0,0, 0,0, 2, 1,0, 3, 2)
- pooler:   (64,128,1,1,9,  0,0,0,0, 0,0, 2, 1,0, 0, 2)   64 tokens x 128 cols, WG g owns cols 64g.., 9 stages
New options vs V's vg (all compile-time; claude/t3/K/kg.py, g256k.py is generated by mkg256k.py):
- WPK 1/2: W prepacked at prepare() into [N/BN][K/64][BN rows][128 B] stage images with the 128B swizzle applied
  (kg.pack_w); one contiguous 1D cp.async.bulk per stage instead of a 2D TMA tile (128 rows at stride K*2 = 128
  DRAM pages). WPK 2 bakes the packed-W address into the code (literal + `%dynamic_smem_size >> 31` runtime zero:
  a plain folded 64-bit immediate lost its high half in some instantiations -> illegal address; ptxas issue).
- PRO 1: fast prologue: init full[0..1] + fence, issue stages 0-1, then the other barriers and stages.
- EPI 2: epilogue straight from the accumulators: per 4 n8-blocks a 4x4 quad transpose of bf16x2 words (4 SHFL)
  gives each lane 16 contiguous bytes of a row -> STG.128 (8 rows x 64 B per warp instruction); no STSM/LDS/bar.
- LASTD D: tail priority: WG1 waits (named barrier 5) before its last D k-blocks until WG0 has finished, so WG0's
  stores overlap WG1's last MMAs; in the solo phases each WG issues its last D k-blocks back to back (no wait,
  no slot release).
- Also built / measured (dead ends below): PF (tensor L2 prefetch of later stages), PFX, PRI (cap on in-flight
  stages at start), EPI 1 (TMA store), NT2 (two 128x64 sub-tiles per CTA with producer-warp stores of sub-tile 0),
  EPF (early prefetch.global.L2 of the first stages), XLD (x of the first 1-2 stages by LDG -> STS from all threads).

## Measured facts (this machine type)
- Timeline (kt.py --trace: globaltimer + clock64 per CTA; means over CTAs, us from the first CTA start):
  V's vg unpooler 128x128 NS6: TMA issue 0.47, consumers start 1.49, first stage landed ~2.0, loop end 22.0-22.3,
  epilogue 0.8 (bar 0.13 + stmatrix 0.23 + stores 0.45-0.58), max-end spread +0.4. o: same start, loop 16 kb, end 7.9.
  The loop itself runs at 96-99 % of the tensor peak at the measured clock (1.63-1.69 GHz) in every config.
  => the losses are start (~1.7 us to the first stage), epilogue (~0.8) and tail (~0.3), not the main loop.
- Cold first-load latency (latprobe.py, 128 CTAs after the flush): 16 KB 2D TMA tile 1.31 us from kernel start,
  16 KB 1D bulk from a baked address 1.10, 4 KB bulk 0.67, 384-thread LDG of 18 KB 0.91; tensor map in global
  memory 1.59 (worse than the param map). prefetch.tensormap: no effect. Flush size (64 vs 512 MB) no effect (not TLB).
- Start probe (startprobe.py, unpooler tiling, 6 stages issued at t=0, stage arrival times):
  x TMA + W TMA 1.77 / 1.82 / 2.30 ...; x TMA first + W 1D bulk from packed W 1.36 / 1.66 / 1.97 ...;
  cp.async (LDGSTS) for W or both: worse (2.18 / 1.79); only 2 stages at t=0: worse (2.01).
  After the first stage the stages arrive every ~0.23 us = 1 MB of distinct W per stage at ~4.5 TB/s (DRAM-bound).
- Per-SM store bandwidth (stprobe.py): 32 KB of bf16 per CTA from smem takes 0.63-0.75 us with STG.128 (256 or 384
  threads), 0.84-0.97 with a TMA tensor store; the same with 16, 64 or 128 CTAs and warm or cold L2 => ~30 B/clk per SM
  store path, not an aggregate L2 limit. This bounds the 128x128 epilogue at ~0.6 us.
- L2 prefetch (cp.async.bulk.prefetch.tensor) of later stages: much worse (o 9.2-11.3 vs 7.9): the extra DRAM
  requests delay the first stages (first data 3.07 vs 1.28 us).
- Instruction fetch is not a factor (icprobe.py: straight-line code runs at 4 clk/IMAD cold and warm).
- GPC: per-GPC loop-end means are within noise of each other; no GPC-specific slowness at 128 CTAs.

## Dead ends (measured)
- EPF (prefetch.global.L2 of the first NS stages of W / x from 128 threads at kernel entry): o 8.40-9.62, unpooler
  23.1-25.1, pooler 33.3-35.9 (vs 7.41 / 21.98 / 22.35): the prefetch instructions stall the issuing warps (thread 0
  issues its TMAs late) and only a few lines are in flight; with ::evict_last also worse.
- XLD (x of the first 1-2 stages loaded with LDG.128 by all 384 threads -> STS, W by bulk): o 7.54 / 7.84 vs 7.55,
  unpooler 22.27 / 22.46 vs 22.13, pooler 22.54 / 22.64 vs 22.43: no gain (the TMA stages that follow land no earlier).
- NT2 (two 128x64 sub-tiles per CTA, x re-streamed, sub-tile 0 stored by producer warps during sub-tile 1): unpooler
  25.5-26.6 vs 22.1, o 8.05-8.10 vs 7.58: the 128x64 sub-tile loop runs at 0.19 us per k-block (84 %) on unpooler
  (pooler with the same 128x64 shape runs at 0.165 = 97 %); cause not found (same SASS loop).
- EPI 1 (TMA tensor store epilogue): o 7.79-7.87 vs 7.65-7.71, unpooler / pooler neutral.
- PF (L2 prefetch), PRI (cap on in-flight stages at start): worse / noise.
- pooler LAY 2 (k-split inside the CTA, n128 wgmma): 22.91 vs 22.48 (LAY1); pooler 128x64 LASTD 2/4: noise / worse.
- Split-K for pooler: not retried (S2 main loop length equals S1's; the exchange is pure overhead; V's notes).
