# WP-32: bs32 specialist (2026-10-27)

Worker WP-32. Base dev/moe_v801.py (bs32 kernel = moe_8_4_1_4_1, (8,4,1) MW 1; SASS-identical in v814). Files:
dev/moe_v830.py (v801 + MOE_WP32_TR item trace, MOE_WP32_NODEP bound; default build = v801 SASS), dev/moe_v831.py
(v830 + MOE_WP32_FST fast start; trace counters moved into the dynamic header), dev/wp32_probe.py (per-CTA budget from
the trace, judge protocol: graph replay, 512 MB L2 flush, jm seeds), dev/wp32_dump.py (offline per-tile / per-CTA view of
a probe dump), dev/wp32_run*.sh. Logs: scratchpad wp32/run*.log; dumps dev/remote_out/wp32_tr*.json.

## 1. Profile (KDA ncu method, profile/v764_ncu, bs32 seed 73736 = 10 experts, 78.5 us under ncu)
- Dim 1 launch: 132 x 384, 1 CTA/SM (216 KB smem, 168 regs), 1 wave: fine.
- Dim 3 stalls: decode lines ~45% of samples (at the instruction floor); long_sb on mbarrier try_wait 14% (consumer data
  waits: the ring is DRAM-paced) + helper warps' sleeps; IPC elapsed/active 1.92/2.08 = SMs idle ~8%.
- Dim 6 memory: DRAM 73.8% of peak averaged over the kernel; the steady state is at the ring rate (below), so the waste is
  where DRAM is NOT busy: start, tail, end.

## 3. Rejected by bound: the G1 -> G2 dependency, G1 order mixing
- MOE_WP32_NODEP (v830; down-stage chunk polls pass at count 0, consumer loops byte-identical): x0.999 (wp32_run1);
  the trace shows 0.00 us of producer dependency spin per CTA on jm routings. Not a lever at bs32.
- Stage-throughput timeline (dev/wp32_bw.py, dev/remote_out/wp32_tr3.json): the ring runs at the DRAM ceiling
  (4.6-4.7 TB/s) only when nearly every CTA is on a 1-group tile; the aggregate falls ~linearly with the number of
  compute-bound 2-4-group CTAs (36 in the first 20 us: 4.1 TB/s; rate ~ 4.68 - 0.016 x #multi-group CTAs). A 1-group
  CTA cannot go above ~1 stage/us (4-slot ring at the loaded DRAM latency), so it cannot absorb the bandwidth the
  compute-bound CTAs leave. Because the loss is linear, spreading the heavy tiles over the G1 waves (tile-interleaved
  G1 order) gains ~0 by this model. Not built.

## 4. Fast start (MOE_WP32_FST), the largest bucket
v801 startup: bitmaps (code 10) 1.66 us, tables 2.46, producer loop top 3.44, first weight copy ~4.7, first data 7.09.
DRAM is idle until ~4.7 us.

| build | change | bench2 bs32 vs v801 (control) | first data | finding |
|---|---|---|---|---|
| v831 | warp 8 issues the first item's 4 stages right after the bitmaps, inside the routing's table barrier | x0.9940 / x0.9959 (0.9968) | 7.78 | the ~2.9 us call held the table barrier: tables 2.53 -> 4.56 us, consumers' entry 3.68 -> 7.20 |
| v832 | warp 8 bar.arrive's a named barrier that replaces that __syncthreads | x0.9993 / x1.0000 (0.9970) | 7.47 | call 1.68 -> 4.77 us holds the producer warpgroup's setmaxnreg.dec, so the consumers' setmaxnreg.inc waits too (entry 3.62 -> 5.36) |
| v834 FSTD | call after the dec | x0.9822 / x0.9819 (0.9970) | 9.26 | a 2.2 us later first stage costs ~2 us of wall time (1:1) |
| v835 | redux.sync selection (was a 1.3 us shuffle ranking); copies stage by stage (stage 0's x rows had queued behind 140 KB of weights in the TMA FIFO) | **x1.0068 / x1.0078** (0.9974) | 5.95 | FST CTAs' first data 4.6-6.0; the 32 wgmma-first CTAs 9.7 (their all-CTA gather waits for the FST CTAs' signaler, which is held in the dec) |
| v836 FDRY | dry pass of the call during the ids load (warm i-cache) | x0.9954 (0.9975; FST x1.0092 same job) | 8.30 | the dry pass held the bitmap barrier (code 10 1.66 -> 3.12 us) |
| v836 FSTW | wgmma first tiles: weights early, gathered x from the producer after the all-CTA gather | x1.0005 (FST x1.0092) | | gather-gated first tiles gain nothing from early weights; the extra early fill slows everyone's cold-code fetches (producer past setmaxnreg.dec 6.5 us, loop entry 8.1) |

Lessons (startup):
- Every startup path is cold code fetched from DRAM after the judge's L2 flush. Once the early fill makes DRAM busy, each
  instruction-cache miss costs ~0.5-1 us, so work that sits on a barrier or on the warpgroup's setmaxnreg must stay
  minimal and come before the fill.
- setmaxnreg couples the warpgroups: the consumers' setmaxnreg.inc (TRY_ALLOC loop) waits until warps 8-11 run
  setmaxnreg.dec, and the signaler (warp 9, XREL's gather release) waits in that same dec.
- Copies leave the SM's TMA unit in issue order: issue stage by stage, so stage 0's x rows are not stuck behind the
  later stages' weights.
- A first stage that completes later costs about 1:1 in wall time (FSTD); one that completes earlier gains ~0.8-0.9 of
  the advance.

## 6. bs128 port (MOE_WP32_FST4, dev/moe_v838.py): rejected
The (8,4,1) MW 4 kernel's first wave is full 32-token wgmma tiles, so its x must wait for the all-CTA gather. FST4: warp 8
ranks the multi-tile experts (redux.sync), posts the first tile's 4 stages (records, arrivals, combined WSC weight +
scale blocks), and the gathered x goes through the loop's existing early-stage path. Consumer loops stay byte-identical
to v814; a call or skip in the producer loop re-scheduled them. wp32_run8: bs128 x0.9915 / x0.9942 (control x0.9962).
check_mt 0 failures. Trace: the early 18 MB weight fill slows the consumers' cold x gather (gather done 4.98 -> 6.86 us,
first data 8.09 -> 9.94). This is the same mechanism that made FSTW lose at bs32: early weights only pay where the first
stage does not wait on the gather.

## 7. Remaining bs32 buckets (for whoever continues)
- Startup with FST: first data ~6.0 us. Still in the way: the consumers' setmaxnreg.inc waits for warp 8's dec (warp 8
  returns ~3.9 us); the 32 wgmma-first CTAs start at ~9.7 us; the producer's loop entry is late (~6.6 us), so the
  first item runs at ~1.1 us/stage instead of 1.02.
- End phase 2.8 us (NO_COMBINE bound x1.017) and tail 2.5-2.8 us (4-stage pieces).
- G2 phase at ~4.0-4.2 TB/s vs 4.6 in G1: split-piece transitions (held AEPI slot ~0.3 us + gap ~0.2 us per 4-stage
  piece) and compute-bound multi-group CTAs (linear loss).

## 8. Why down-projection stages average 1.10 us vs 1.03 (planner task 2; v837 base, dev/moe_v840.py, v841.py)
Timing-only bounds on the bs32 kernel (consumer loops byte-identical to v837), bench2 bs32 vs v837 (control ~0.997-0.999).
None moves the shape:

| bound | ratio |
|---|---|
| NOX2: no intermediate copy | x1.0004 |
| XRES: intermediate from one hot L2 block | x0.9967 |
| W13: down weights + scales from the gate/up tensors in the gate/up layout | x0.9972 |
| NOEPI2: no down epilogue stores | x0.9969 |
| NOPOLL: no readiness poll | x0.9973 / x0.9982 |
| NOFENCE: poll without its proxy fence | x0.9973 |

The intermediate copies (L2), the w2 tensor or its layout, the y / KRED epilogue stores and the readiness poll are not
the cause.

Per-stage trace (MOE_WPN_TRACE), split by stage position (dev/wp32_stage.py; cycles; mean/median):

| bs32 72603 | first stage | middle stages | last stage |
|---|---|---|---|
| gate/up 1-group whole items: period / gap | 4006 / 2083 | 1840 / 284 | 1771 / 275 |
| down whole items | 4527 / 2481 | 1799 / 249 | 1724 / 248 |
| down 4-stage k-split pieces | 3305 / 1481 | 1795 / 231 | 1757 / 239 |
| producer: slot acquired - previous stage's copies issued | 1850-1940 | 470-630 | 570-680 |

bs128 (seeds 71637, 72808) looks the same: middle down stages 1797-1861 vs gate/up 1764-1801; first stages 3050-3500.

- Down stages are not slower. A middle stage of a down item runs at the gate/up period or faster.
- Every item pays ~1300-2300 cycles at its first stage. The producer arrives at that stage's slot ~1300 cycles late
  because its per-item path (168 SASS instructions: claim, decode, tile lookup, address arithmetic for every case)
  runs on SMSP0 next to two decode-bound consumer warps. That stage's slot had been free for ~2600 cycles.
- At bs32 the down phase is mostly 4-stage pieces (4.4 per CTA, 9 tiles), so the same per-item cost lands on 4x fewer
  stages. That is the "7%".

Fix direction (not built): take the per-item setup off the item boundary.
- (a) Warp 9 (the signaler, idle between signals) decodes the item the producer already claimed and writes a compact
  per-item descriptor (weights / scales / x sources, strides, record fields) into a 2-entry shared-memory ring. The
  producer's boundary then becomes 2-3 LDS plus pointer bumps.
- (b) A full PNEXT that also precomputes the pointers before the item's last slot wait. The existing MOE_PNEXT=1
  re-schedules the bs32 consumer loop (similarity 0.38) and spills at MW 4.
- Either needs a SASS check that the consumer loops stay identical.
- Expected: about 0.2-0.25 us of the per-item gap (graph-mode probe) times ~9 items per CTA, i.e. ~1% at bs32, less at
  bs128/256 (16-stage items).

## 9. Per-item boundary, producer side: the aggregated claim atomic (dev/moe_v860.py MOE_WP60_INC)
- The producer claims its next item with a predicated lane-0 "@p atom.global.add.u32". The source comment says inline
  PTX was chosen to avoid warp aggregation, but NVRTC 13.0.88's ptxas still aggregates it: VOTEU / FLO / POPC, ATOMG,
  then SHFL.IDX of the result right after the ATOMG. So the producer waited for the claim's L2 round trip at the top
  of every item.
- Every add form is aggregated: relaxed / acq_rel / sys, inside an if (lane == 0), and inc with bound 0xffffffff, which
  ptxas rewrites to add. CAS, EXCH and a bounded inc are not.
- MOE_WP60_INC uses atom.global.inc.u32 with bound 0x7fffffff (never reached; the queue head is zeroed every call).
  The result is first used at the item's end. Every main kernel's consumer and producer stage loops are byte-identical
  to v837.
- Trace: at bs32 the producer reaches a first stage's slot 550-600 cycles sooner (slot-acquired minus previous copies
  1870-1944 -> 1290-1340 cyc). The first-stage gap barely moves (2174 -> 1932 for gate/up items; 1563 -> 1514 for
  pieces) while issue -> data-ready grows by the same ~500 cycles. The data was already there; the consumers were not.
- bench2 (wp32_run11, all shapes, vs v837 x2): within the control spread at every shape.
- Remaining transition cost is consumer-side: the item-end staging (consumer_sync of the 8 warps, paced by the SMSP0
  pair, accumulator stores and the hand-off to the epilogue warps) before the next item's first wait. WP-W measured
  the alternatives (PWS, AREL, SEPI8, BSTG) without gains. The planner's descriptor ring would only remove producer
  time that is already hidden, so it was not built.

## 10. bs8 / bs16 startup (planner task 4; dev/moe_v900.py stamps, v901 MOE_WP32_EIDS)
The (4,1,1) / (4,2,1) kernels already have an off-barrier fast start: MOE_EARLY_ALL / EARLY_NT2. Producer warp 8 skips
the routing, works out its first item from the ids itself, and issues the first MOE_EARLY_NS = 2 stages (weights block +
per-token x rows) before warps 0-7 finish routing. So no FST port is needed.

wp32_run12 traces (8 seeds; mean of per-seed medians, us):

| | dec | early-path entry | first item worked out | 2 stages issued | consumers past eis | first data |
|---|---|---|---|---|---|---|
| bs8 | 1.07 | 1.31 | 2.23 | 2.88 | 3.32 | 5.22 |
| bs16 | 1.15 | 1.41 | 2.19 | 2.66 | 3.14 | 4.27 |

- First copy issued at 2.7-2.9 us. P7's minimal kernel issues at 2.4 us when it depends on the ids bitmap, and at
  1.7 us from entry with no dependency. So bs8/16 are within ~0.3-0.5 us of the floor.
- First data lands 1.6-2.3 us after issue: the DRAM fill plus cold page and TLB costs, the same as a bare ring.
- MOE_WP32_EIDS (ids loaded at entry) does not move "worked out" (2.23 -> 2.32 us). The ~1 us between the early-path
  entry and "worked out" is cold instruction fetch of that code after the L2 flush, not the ids load.
- MOE_EARLY_NS=3 loses: bs8 x0.988 / x0.992.
- Remaining prize: ~0.3-0.5 us at bs8/16 (0.5-0.8% bs8), with no mechanism that avoids cold code fetch. Closed.
